# Spec: 状态徽章样式单源 —— 消除三份颜色拷贝

> Triage label: `ready-for-agent`

## Problem Statement

六状态 × 明暗双套 × 段位徽章的 CSS 颜色块（约 70 行），在 3 个画廊组件里逐字拷贝：

1. `src/components/SteamGallery.astro`
2. `src/components/GamesTableOfContents.astro`
3. `src/components/GamesMobileTableOfContents.astro`

问题从用户视角是：**改一个徽章配色要三处同改，漏一处就出现"这一屏金色、那一屏还是旧的灰色"的视觉漂移。** 三份拷贝加起来约 210 行，是纯粹的浅层重复。

## Solution

把状态的六态 + 明暗 + 段位徽章样式收敛到一个**单一共享样式来源**，三个组件共同引用。改动一处配色，三处展示点同步生效。样式事实从此单源。

## User Stories

1. 作为画廊访问者，我希望无论看卡片还是右侧列表，同一状态的徽章颜色完全一致，以免产生"两张不同表"的困惑。
2. 作为画廊访问者，我希望在暗色与亮色主题下徽章都保持可读（明暗双套），以免某主题下看不清状态。
3. 作为博客所有者，我希望调整某一状态的徽章颜色只改一处，全部展示点同步更新，以免漏改造成视觉不一致。
4. 作为博客所有者，我希望在移动端下拉列表、桌面侧栏、卡片墙上看到完全一致的状态色彩语义，作为统一的视觉语言。
5. 作为开发者，我希望徽章样式与徽章词汇/规则放在相近的单一事实源，以便"改状态时想到改徽章"。
6. 作为测试者，我希望确认三处展示使用相同颜色来源，从而能通过一次变更验证全部展示点。

## Implementation Decisions

- **样式承载**：把六态（暗）+ 六态（亮）+ 段位徽章（rank）的 `status-badge` 规则抽到单一共享样式文件（如 `src/styles/` 下新增，或并入 `theme.css`，通过 Starlight 的 `customCss` 全局引入）。
- **作用域**：徽章规则用全局选择器（如 `.status-badge[data-status=...]`），三个组件通过 `:global()` 或共享样式命中，不再在各自 scoped 样式块里重复。
- **组件移除重复**：三个组件删除各自 ~70 行的徽章颜色块，仅保留组件特有的布局/间距样式。
- **顺序依赖**：本 Spec 可在候选 2（词汇单源）之前或之后落地——颜色单源与词汇单源可独立；若候选 2 先落地，徽章类名（`status-badge` / `rank-badge`）已由词汇模块统一，本 Spec 只统一颜色规则。
- **明暗双套保留**：`:root[data-theme='light']` 及默认暗色的两套规则都移入共享样式，不可丢失。
- **领域术语保持**：继续使用 游玩状态 (Play Status)、段位 (Rank)。

## Testing Decisions

- **测试性质**：样式单源难以用单元测试直接断言，采用构建 + 人工核对的方式验证。
- **验证手段**：`npm run build` 成功；`npm run dev` 后访问 `/games`，核对卡片墙、右侧列表、移动端下拉三处的六态徽章颜色一致，且暗/亮主题各检查一轮。
- **好测试的标准**：对外行为——"同一状态在三个展示点视觉一致"，而非样式实现细节。
- **现有测试先例**：组件无明显样式单元测试；此前通过 `npm run build` + `npm test` + 本地 `npm run dev` 肉眼确认（README 所述流程）。
- **架构缝**：样式单源处（共享 CSS），无 DOM/交互依赖。

## Out of Scope

- 不改徽章的颜色取值本身——仅收敛其定义位置。
- 不改徽章的尺寸、圆角、内边距等布局细节（除非单源化时顺手对齐，需在 PR 里注明）。
- 不改六阶梯词汇（属候选 2）、不改气泡渲染（属候选 1）。
- 不改排序逻辑、联动协议。
