# 工程与编码规范 (Engineering & Coding Standards)

> 本规范定义本博客系统（Astro + TypeScript + Starlight）的架构设计、代码编写、类型安全与测试纪律。所有功能演进与重构均须恪守本文档中的约定。

---

## 一、架构设计原则 (Architectural Principles)

### 1. 深度模块化 (Deep Modules)
- **少量接口，大量实现**：模块应向调用方隐藏内部复杂度（例如：`gallery-coordinator.ts` 内部纳管事件监听、DOM 节点索引、手风琴切换与三处 DOM 排序，但仅暴露精简的初始化接口与动作方法）。
- **杜绝浅层包装**：避免为了“看起来规范”而创建仅做参数透传的空壳模块。如果删除一个模块并没有让复杂度分散到各处，说明它是冗余的。

### 2. 单一事实来源 (Single Source of Truth)
- **业务词汇单源**：六阶梯游玩状态（`Status`）、中文标签、排序权重与映射关系**唯一归属** `src/lib/play-status.ts`。UI 组件、CLI 工具、CSV 转换脚本及测试代码必须从该模块导入，严禁在业务端硬编码文案。
- **视觉主题单源**：所有状态徽章与段位徽章的配色（明暗两套）**唯一归属** `src/styles/theme.css`。任何局部 Astro 组件仅保留自身的间距与字号排版，不得自建重复的颜色规则。
- **数据加载与预排序单源**：数据文件合并与排序预设由 `src/lib/steam-data.ts` 统一计算并实行模块级缓存，避免在各渲染点重复发起文件 I/O 或多次重排。

### 3. 组件与交互契约 (Component Contracts)
- **模板纯静态化**：Astro 组件应尽可能退化为声明式纯模板，仅负责输出带有结构化数据属性（如 `data-appid`）的静态 HTML。
- **消灭私有选择器窥探与网状事件**：多组件间的复杂交互禁止使用分散的 `window.CustomEvent` 网状触发，严禁在一个组件中通过选择器直接操控另一组件的内部 DOM。所有跨容器状态与重排由深度协调器（Coordinator）统一调度。

## 二、TypeScript 与编码纪律

### 1. 严格类型安全 (Strict Type Safety)
- **零宽松容忍**：严禁使用 `any`、`as any`、`@ts-ignore` 或 `@ts-expect-error` 来压制类型报错。所有类型必须在编译期自恰。
- **运行时环境自适应**：在客户端与测试端两用的核心模块（如协调器）中，DOM 相关的节点判定应封装保护辅助函数（如 `isHtmlElement`），确保在 Node.js 测试环境（无默认 `HTMLElement` 声明）和浏览器真实环境中均能平滑运行。
- **导入扩展名明确**：纯 TypeScript 工具脚本在 Node 环境下运行时，配合 `--experimental-strip-types`，导入相对模块应显式保留完整扩展名。

### 2. 代码风格与整洁度
- **变量与函数命名**：遵循意图明晰原则（如 `loadMergedGames`、`resolveTaskCommand`、`checkPrerequisites`），不使用含糊缩写。
- **函数职责单一**：一个数据处理函数不应同时负责拼装上百行的 HTML 字符串；领域逻辑与展示标记必须物理分离。

## 三、测试与质量准则 (Testing Discipline)

### 1. 仅测试外部行为 (Interface Testing)
- **黑盒验证**：测试用例只对模块公开暴露的接口、输入与最终产生的行为（如 DOM 类名切换、返回值格式、排序结果）进行断言，不探测或耦合模块内部的私有临时变量。
- **接口即测试面**：调用方与测试用例跨越同一道接缝。如果为了测试必须强行导出内部辅助函数，通常说明模块的设计形状需要深化。

### 2. 杜绝破坏性副作用
- **非破坏性环境**：单元测试绝不应采用重命名物理生产文件（如将真实数据文件临时改名为 `.bak`）的破坏性方式来模拟失败。
- **适配器解耦**：需要模拟文件 I/O 失败或极端边界值时，应通过存储适配器接缝（Storage Adapter）注入内存假数据或模拟异常，保障测试运行在任何中断时刻均不污染真实数据。

### 3. 测试套件门禁
- 任何业务逻辑扩展必须伴随回归测试用例。
- 代码提交前必须确保：
  - `npm test`：100% 通过（所有测试套件零错误）；
  - `npx astro check`：静态检查零报错（0 errors）。

## 四、Git 提交与发布规范

### 1. 语义化提交格式 (Conventional Commits)
提交信息采用中文，严格包含语义化前缀：
- `feat`: 新增功能特性（如新增协调器、添加交互菜单）
- `fix`: 问题修复（如修复气泡重复累积、修复移动端排序脱节）
- `style`: 样式调整与外观优化（不影响代码逻辑）
- `perf`: 性能优化与缓存改进（如模块单例缓存）
- `refactor`: 重构优化（既不新增功能也不修复问题的结构重组）
- `docs`: 文档变更（规范、README、ADR、注释）
- `chore`: 依赖维护、自动化数据同步、忽略规则配置

### 2. 提交原子性
- **数据与代码解耦提交**：`src/data/steam_annotations.json` 的手写数据变更，应尽量与系统代码（`.astro` / `.ts`）的重构提交拆分为独立的 commit，以便清晰追溯。
- **禁止提交临时文件**：`steam.csv`、本地 `.env`、编译产物等绝不允许强行入库。
